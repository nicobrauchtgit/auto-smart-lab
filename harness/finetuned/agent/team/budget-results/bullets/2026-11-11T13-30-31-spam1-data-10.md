**Inputs: what an email file actually contains** (from `research/dump.py`, `research/stats.py`)

- Training: 16 662 email files (8 360 ham / 8 302 spam, so ~50/50 — matches `training.targets`); test: 15 051 files. Sizes 136–27 966 B train, 137–228 386 B test (`training.sizes`, `test.sizes`).
- Every training and test file starts with `Subject:` and contains **no other headers**: a header-line scan over all 16 662 training files found only `Subject` (16 662 hits) and zero hits for `From/To/Date/Cc/Received/MIME-Version/Content-Type/X-…`. So no header metadata features exist — only subject line + body text (`research/stats.py`).
- Body/subject lengths are essentially equal across classes (train mean 1 462 vs 1 458 chars); only subject length differs slightly (39 vs 47 chars). Median lines 20 (ham) vs 15 (spam) (`training.text_by_target`, `research/stats.py`).
- Content is pre-normalized plain text, all lowercase, with spaces inserted around punctuation and tokens (`15 745`/16 662 files contain `" . "`, e.g. `5 . 0`, `$ 279 . 99`). All files decode as clean UTF-8 (`utf8_fraction` 0.998/0.999; no encoding problem).
- URLs are present but **never** as `http://`: they appear as `http : / / host . com / path`. Raw `http://` occurs in 0 files, while the spaced form occurs in 3 413 train files (712 ham vs 2 701 spam) and 2 741 test files. The profile's `urls` count of 0 for every split is an artifact of that spacing, not an absence of links (`research/stats.py`, profile `training.text.urls`).
- Punctuation/space normalization means naive regex features (URLs, phone numbers, `.com`, currency) need a space-tolerant pattern or a whitespace-stripped copy of the text.

**Signal and traps in the text** (from `research/stats.py`)

- `enron` occurs in **53.3 % of ham, 0.0 % of spam** in training, and 19.9 % of test files. It is effectively a perfect class indicator on train; treat it as a strong but potentially distribution-fragile feature.
- Consistent with two source corpora (Enron ham + 2004–2005 spam), year tokens are asymmetric: `2004` appears in 15 ham vs 922 spam files, `2005` 8 vs 392. Any model can latch onto document year — check whether the test set keeps this pattern.
- Other high log-ratio spam terms: `viagra`, `unsubscribe`, `dollars`, `free`, `click`, `cheap`, `mortgage`, `promotional`, `weight`, `doctor`; ham terms are mostly Enron person/office names (`ect`, `forwarded`, `cc`, `vince`, `houston`, `sally`, `lunch`).
- Vocabulary: 146 032 distinct tokens in train, 115 425 in test; **3.47 % of test tokens are unseen** in train, and 68 001 distinct test tokens are unseen — consistent with the random string/token injection typical of this spam corpus, so heavy stemming/char-ngram tolerance matters more than exact word matching.
- Test documents are longer-tailed than train: mean 293 tokens vs 234, but median 120 vs 138 (profile `test.sizes` max 228 386 B and `test.text.lines` max 2 648 vs train max 517 lines). Long test inputs exceeding anything in train may need a length/truncation policy.

**Data hygiene**

- Training is order-unbiased: target counts per archive-order quarter are 2103/2062 … 2095/2072, no ordering leak (`training.order_leakage`).
- No duplicates: 16 662 distinct contents in train, 15 051 in test, 0 duplicate groups, 0 cross-split exact overlap, 0 duplicate target conflicts (profile `*.duplicates`, `training.duplicate_target_conflicts`, `training_vs_test.exact_overlap`). So no dedup work is needed, but also no free test-set leakage to exploit.
- 412 training and 97 test files contain control characters (`\x01` × 2 598, `\x00` in 51 files, plus `\x0f/\x06/…`), and 622 training files contain non-ASCII bytes (`´`, `·`). A strict `str.isprintable()`/ASCII-only cleaning step will silently damage these; use `errors="replace"` and tolerate them. This is likely why the profile labels 11 train / 28 test members as `binary` (`*.content_types`) even though no file has a real magic-byte signature — my own magic-byte scan found 0 binary files (`research/dump.py`).
- **Trap:** `spam1-train.zip` contains 16 663 members, not 16 662 — the extra entry is the `spam1-train.labels` file itself, which has no `.0`/`.1` suffix. Naive "read every member and split label off the filename" code raises `ValueError: invalid literal for int() with base 10: 'labels'` (reproduced in `research/stats.py` before filtering, member count confirmed in `research/dump.py`). Filter members by suffix, and don't count the zip's member list as sample count.
- Labels are recoverable from the training filenames: 16 662 `.labels` entries agree with the name suffix with 0 mismatches (`research/dump.py`); test names all end in `.x` and carry no information (profile `training_vs_test.name_suffixes`).
