- Data layout: members are `data/spam2-train/<16 lowercase chars>.<0|1>` and `data/spam2-test/<16 chars>.x`; names are random apart from the label suffix (`profile.training_vs_test.name_suffixes`: 0=5682, 1=13074, x=12469; my listing of both zips). The `.labels` file is also *inside* `spam2-train.zip` as a namelist entry (`spam2-train.labels`, 18757 namelist entries), so exclude it when iterating.
- `spam2-train.zip` member order matches the `.labels` file line-for-line (`data/spam2-train/yrkspdlxsysxzhuq.0;0`), so labels can be read from either source; both agree with `profile.training.targets` (69.7% spam).
- Both archives are stored uncompressed: `compress_size == file_size`, ratio 1.00 (zip info dump). No decode step needed for archive access.
- Every input is a complete RFC-822 message (`email_header_rate` 1.0 in train and test, `profile.*.text`) but header blocks are *large*: mean 2331 B for ham vs 1106 B for spam, 1552 B for test (research/inspect2.py) — roughly 15–30% of the file is headers, so header metadata is a first-class feature source.
- Header fields that sharply separate classes (500 messages per class, research/inspect2.py, % of messages containing the field): list-id 77.2 ham / 1.6 spam; list-unsubscribe 78.0 / 2.4; precedence 78.0 / 2.8; in-reply-to 45.2 / 0.0; references 46.8 / 0.0; `x-be…` 50.2 / 1.6; x-spam-ish 67.2 / 4.0; dkim-signature 9.2 / 0.0; content-disposition 25.2 / 0.4; sender 70.4 / 12.2; reply-to 63.8 / 21.8; and inverted for x-mailer 21.2 / 70.4 and x-priority 3.4 / 49.0.
- `Received` header count is itself informative: 934 occurrences across 500 ham (1.9/msg) vs 418 across 500 spam (0.8/msg) (research/inspect1.py/inspect2.py census).
- Structure differs: ham is mostly `text/plain` (138/200) while spam skews to `multipart/alternative` (76/200), `multipart/related` (47/200) and `text/html` (36/200) (census on 200/class, research/inspect1.py); consistent with `profile.training.text_by_target` html_rate 0.216 ham vs 0.765 spam. `multipart/signed` and `multipart/report` appear (5 and 1 of 200) — signed bodies need care.
- Encodings: `us-ascii` dominates ham (100/200) and `iso-8859-1` the rest; spam additionally shows `windows-1250/1251/1252`, `iso-2022-jp`, `gb2312` (research/inspect1.py). Strict UTF-8 decoding fails on 100/500 spam and 52/500 ham (106/500 test) — decode per declared charset or with `errors="replace"` (research/inspect2.py).
- Traps on non-text bytes: 50 training members are flagged `binary` by magic bytes (`profile.training.content_types.categories`), 0 in test; 3/500 sampled spam contain NUL bytes; 8 of ~1500 sampled files contain control bytes in the body, e.g. ISO-2022-JP `ESC $ B` sequences (research/inspect2.py). Also base64 in 5/500 ham vs 0/500 spam and quoted-printable 38/500 ham / 14/500 spam / 30/500 test — a minority of bodies are encoded.
- MIME part headers are sometimes malformed/stripped (bare `Content-Type: text/plain;` lines after a boundary, no value) — seen in the control-char dump of `data/spam2-train/vbhqrimvhgzitbwc.1`; lenient parsing is safer than a strict one.
- No duplicates and no leakage: 0 duplicate groups within train, 0 within test, 0 conflicting-label duplicate groups, and 0 test members whose SHA-256 occurs in training (`profile.training.duplicates`, `test.duplicates`, `training.duplicate_target_conflicts`, `training_vs_test.exact_overlap`). No dedup or leakage guard needed.
- No ordering artifact: spam rate is flat across quarters of archive order (q1–q4: 3233/3262/3274/3305 spam, `profile.training.order_leakage`), so a plain random split is fine.
- Weak but real metadata signals: median size 3611 B spam vs 4425 B ham while mean is larger for ham (8762 vs 7645; ham p95 31602 vs 26245) — ham has big outliers (`profile.training.sizes_by_target`); URL count median 5 ham vs 2 spam (`profile.training.text_by_target.urls_median`).
- Test looks like a mixed draw rather than a different population: its header rates sit between the two train classes (list-id 29.6%, precedence 30.8%, x-mailer 57.2%, x-priority 36.2%, content-disposition 9.6%, in-reply-to 17.8%, dkim-signature 3.0%, research/inspect2.py on 500 test), and size/html stats sit between them (mean 7746 B, html_rate 0.538 vs 0.599 train). Nothing indicates a distribution shift beyond class mix; the class prior is the main thing not verifiable from the test files.
