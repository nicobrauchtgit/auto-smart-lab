- **Every member is a single RFC-822 message with a leading mbox `From ` line**: all 18,756 train members start with `From <envelope> <date>`, and profile `*.text.email_header_rate = 1.0` for both splits (`research/deep.py`, "members not starting with 'From ': 0"). Test members are the same format (`profile.test.content_types.categories = {email: 12469}`) but named with `.x` (`profile.training_vs_test.name_suffixes`).
- **Labels are readable two ways and agree**: `spam2-train.labels` has 18,756 `data/spam2-train/<16-char-token>.<label>;<label>` lines, matching the filename suffix (`head` of the labels file; `profile.training.targets`: 13,074 spam / 5,682 ham = 69.7% spam). `spam2-train.zip` actually contains `spam2-train.labels` as a 18,757th member — a reader that globs the archive gets a non-CSV extra file.
- **Training dates are Apr–May 2007, test dates are Jun–Jul 2007** — no date overlap (`research/dates_xss.py`: train spam/ham month counts 2007-04/05, test 2007-06/07). Any date/recency feature is untrainable on the test window.
- **Header presence is the most discriminative structured signal and transfers to test** (`research/full_headers.py`, full-corpus rates, spam% / ham% / test%): `precedence` .03/.79/.34, `list-id` .02/.77/.33, `x-spam-status` .006/.66/.26, `sender` .04/.55/.24, `errors-to` .03/.53/.23, `x-beenthere` .02/.51/.22, `references` .002/.47/.20, `in-reply-to` .001/.47/.19, `x-mailman-version` .02/.49/.22 vs spam-side `x-mailer` .70/.23/.57, `x-priority` .50/.04/.38, `x-mimeole` .52/.14/.35, `x-msmail-priority` .36/.03/.23, `x-uuid` .29/.000/.22, `x-miltered` .29/.0004/.22, `x-virus-status` .29/.005/.22, `x-antiabuse` .08/.005/.013.
- **`X-Spam-Status` is a valid header signal, not a verdict leak**: across samples it is only ever `No, hits=…`/`No, score=…`, never `Yes` (train spam 0/1200, train ham 0/791, test 0/371 present) — presence, not the SpamAssassin decision, correlates with ham (`research/dates_xss.py`, `research/deep.py`).
- **Hop count differs**: `Received` appears 2.15× per spam message vs 4.63× per ham (sample of 1500 each, `research/hdr_stats.py`); test is in between at 3.29.
- **MIME structure separates classes**: multipart in 937/1500 spam-sample vs 298/1500 ham-sample; spam is `multipart/alternative`+`multipart/related` with `text/html`, ham is mostly `text/plain` (`research/hdr_stats.py`; profile `training.text_by_target` html_rate 0.765 spam vs 0.216 ham). Base64 bodies 113/500 spam vs 13/500 ham, quoted-printable 243 vs 56 (`research/deep.py`).
- **Encoding is a real trap**: only 83.7% of train / 83.9% of test members are valid UTF-8 (`profile.*.content_types.utf8_fraction`), so ~16% of members need latin-1 or charset-aware decoding; spam declares exotic charsets (`iso-2022-jp`, `gb2312`, `windows-1250/1251`, `koi8-r`) far more than ham (`research/hdr_stats.py` charset tables). RFC2047 encoded-words are only in ~4% of members (`=?…?B?…?` in 38/900 spam and 31/900 ham subject lines, `research/enc_domains.py`).
- **Naive regex parsing traps**: quoted-printable `=` shows up as `charset=3Diso-8859-1`, `charset=3dus-ascii` etc. (`research/deep.py`), and the test sample contains garbage header values — `Content-Type: 44-bit`, `Content-Transfer-Encoding: 2-bit / 27-bit` (`research/hdr_stats.py`). Header names must be read as structured fields, not substring-matched.
- **Recipient-address artifact is strong but corpus-specific**: spam `To:` lands on uwaterloo mail machines (`speedy`, `plg`, `flax9/plg2 .uwaterloo.ca`), ham `To:`/`Delivered-To:` goes to mailing lists and external orgs (`perl.org`, `stat.math.ethz.ch`, `samba.org`, `gmail.com`); test shows both patterns (`research/enc_domains.py`).
- **Sizes are similar across splits but with different tails**: train median 3,946 B vs test 3,929 B (profile sizes), ham median 4,425 vs spam 3,611, spam min 1,005 vs ham min 1,574 (`profile.training.sizes_by_target`); test max 674 KB / 15,125 lines exceeds train max 547 KB / 7,141 lines, so test has larger HTML/base64 blobs at the p95+ tail.
- **No duplicates or cross-split leakage, and no ordering leak**: 0 duplicate contents in either split, 0 train∩test content matches, 0 label conflicts, and the spam share is flat across archive quarters (`profile.training.duplicates`, `test.duplicates`, `training_vs_test.exact_overlap = 0.0`, `training.order_leakage` ≈ 69% in every quarter).
- **Two profile-vs-reality caveats**: profile `training.content_types.categories.binary = 50` appears to be heuristic noise — every train file begins with `From ` and 9,000 checked had no binary control bytes in the first 400 body bytes (`research/deep.py`); and no body contains a stray `\nFrom ` mbox line (0/3200 scanned, `research/enc_domains.py`), so message-boundary splitting is not needed since files are already one message each.
- Scripts written and run: `research/hdr_stats.py` (header/content-type stats by class), `research/deep.py` (mbox/MIME/binary sniffing), `research/dates_xss.py` (date ranges, SpamAssassin markers), `research/enc_domains.py` (UTF-8/RFC2047/recipient domains), `research/full_headers.py` (full-corpus header presence per class).
