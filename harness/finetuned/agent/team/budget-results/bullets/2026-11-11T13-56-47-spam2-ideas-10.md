- Training corpus is **raw, unparsed RFC-822 mail** (~18,757 files in `units/01-spam/spam-detection-in-practice-50-points/data/data/spam2-train/`), not clean bodies: `From ` mailbox-line, `Return-Path`, multi-hop `Received:` chain, `X-Mailer`, `Message-Id`, `Content-Type: multipart/related`, `quoted-printable` HTML body, and a `------=_NextPart_…` boundary (`data/.../ngvfuarcusgyuxpy.1`, read 10 Apr 2007). Parse with the stdlib `email`/`mailbox` package rather than splitting on the first blank line, and keep header-derived features separate from body-derived features.
- **Multipart/encoded bodies are the norm** — the only text part is `text/html` in `quoted-printable` (`=3D` escaping), `charset=iso-8859-1`. A pipeline needs: walk `get_payload(decode=True)` over parts, decode transfer-encoding + charset, then strip HTML tags to recover visible text. Missing this loses the entire message content for the files that matter most.
- **Headers alone are a first-class feature space here** (task.md explicitly says you'll "encounter different headers and formats"): sender/`Return-Path` domain and TLD, `Received` relay path, `X-Mailer`/`X-MimeOLE` client fingerprint, `Message-Id` domain vs. `From` domain mismatch, `Date` vs. received-date skew, `Status: O`/`Lines:`/`Content-Length:` metadata.
- **Body-content signals from the observed spam type**: pump-and-dump stock spam (`Symbol: CPMM`, `Close: $0.28 UP +7.69%`, "Volume Up 120.7%") written in HTML — so HTML-derived features (tag count, `<FONT>`/`<B>`/`<U>` density, `<IMG>`/link counts, displayed-text-vs-href mismatch, `DOCTYPE` boilerplate) plus financial-token bag will carry the class.
- **One spam file ends with a stray single-token line after the MIME close-boundary** (`mWFeanigs`, `ngvfuarcusgyuxpy.1`). Worth a fast systematic check across both splits for corpus artifacts/watermarks before trusting any feature — the label is also encoded in the filename (`task.md`: files end in their label), so accidental filename-derived leakage would look great in CV and fail on `.x`.
- **Read as bytes, decode leniently** (`bytes`, then `errors="replace"` after charset lookup): the corpus spans 2005–2007 mixed `iso-8859-1`/`us-ascii`/`utf-8` bodies, and a strict UTF-8 read will throw on some files.
- **Size it for parallel I/O**: ~18.8k small files for train plus a same-sized `spam2-test/` tree — parse once to a cached feature table (`joblib`/persistent store) so model experiments don't re-walk the corpus; joblib is already declared in `pyproject.toml`.
- **Class balance / thresholding**: verify the ham:spam ratio in `spam2-train.labels` (labels are in the filename and mirrored per line there, e.g. `…ngvfuarcusgyuxpy.1;1`). Scoring is "identical to the first task" (`task.md`) and unknown to me, so keep a probability calibration/threshold step tunable rather than committing to argmax before knowing the metric.
- **Split by sender/domain, not by file index**: 2007 bulk spam arrives in tight bursts from the same hosts (same `Message-Id` prefix, same `X-Mailer`, same `Received` relay), so random shuffling inflates CV. Group-split on sender domain or `Message-Id` to get an honest estimate.
- **Test-file handling**: test files end in `.x` and the ending carries no label information (`task.md`); glob both splits with the same parser and don't branch feature logic on the extension.
- Only two reference slides are available locally (`resources/smartlab-spam.txt`, `mlsec-perf-small.txt`); I did not get to them within budget, so their stated metric/formula should be read by the builder rather than assumed.
