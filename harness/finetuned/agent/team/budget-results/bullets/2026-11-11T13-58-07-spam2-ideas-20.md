- Emails are raw, unparsed RFC-822 messages, one file per message: mbox-style `From ` envelope line, full `Received:` chains, MIME headers, then body — `data/data/spam2-train/aaepiyrtiikazteg.1`, `aaeaggzkerfbhepy.0`. Labels come from `data/spam2-train.labels` in `path;label` (semicolon-separated) form, and ~18.8k labeled messages exist, so this is a large corpus where a light model is fine.
- Dates in the two files I read are Apr–May 2007 (uwaterloo `speedy`/`flax9` hosts, ClamAV 0.90.x, SpamAssassin 3.1.8) — a mid-2007 public spam/ham corpus, not a modern one. Treat any "spam words" intuition from 2020s corpora with caution.
- Bodies are heterogeneous: `text/html` with inline CSS/tracking images (`aaepiyrtiikazteg.1`), plain text with `format=flowed` quote chains (`aaeaggzkerfbhepy.0`), and `multipart/alternative|mixed|related|signed` in both splits (e.g. `spam2-test/nxmjenatsjcirzrt.x`, `spam2-train/boucfissqxyzbkrj.0`, `sapgxdblaceeyoxr.1`, `iyitlyhjkabodynl.1`).
- Files are not clean UTF-8 — the French spam shows replacement glyphs for accented characters. Read bytes and decode with `errors="replace"` before tokenizing.
- **Parsed `X-Spam-Status` as a numeric feature, normalized per host.** The header appears in both train and test with different syntaxes and thresholds — `score=… required=3.7/4.0/5.0` vs `hits=… required=8.0/2.5` (`spam2-train/yeourninwpqopaxm.x`… i.e. `spam2-test/yeourninwpqopaxm.x`, `spam2-train/pehfnaxyljeozerj.0`, `spam2-test/fgdtesqqufmyayeq.x`). Raw scores are not comparable across gateways, so divide by `required` or binarize per threshold instead of feeding the raw number.
- **The named SpamAssassin tests as a categorical/vector.** Values list symbolic tests (`BAYES_00/50/99`, `ALL_TRUSTED`, `SPF_PASS`, `DKIM_SIGNED`, `FORGED_RCVD_HELO`, `RCVD_IN_DSBL`, `HTML_80_90`, `BOGOFILTER/BOGO_SPAM`) — a compact, cheap bag-of-rules representation.
- **Important caveat: that verdict disagrees with the ground truth.** Many messages labelled `0` carry `X-Spam-Status: Yes` (`spam2-train/sxdplorhmtishucp.0`, `lugmguxixicyxcwl.0`, `zeqmxaiosyjavrbu.0`, `ubucabxmddcazuum.0`, `myjdsgmnlnejlklc.0`), and the same header family shows up in the test set (`spam2-test/xuudzckxwppavvge.x`, `kqwuwvvzlqrczmps.x`, `pcltxurdcegfymps.x`). So it's a strong prior, not an oracle: keep it as one feature among text, use the `spam2-train.labels` values as the reference, and never hard-rule on the embedded verdict.
- **Header-derived metadata features**, separate from the body: `From` display name and domain, `To`/`Reply-To` (the spam sample has an empty `Reply-To:`), `Subject`, `List-Id`/`Mailing-List`/`Precedence: bulk` (list-mail ⇒ overwhelmingly ham), `X-AntiAbuse`, `Content-Type`/`Content-Transfer-Encoding`, `Message-ID` domain, number of `Received:` hops. This matches the unit's "words *and metadata*" framing (`resources/smartlab-spam.txt`, slide 2).
- **Body text after real parsing** — decode the `text/*` parts of multipart messages, strip HTML tags (bs4 is a declared dependency), decode quoted-printable/base64, then TF-IDF word/char n-grams per the course tips (`resources/smartlab-spam.txt`, slide 4). HTML-vs-plaintext alone is a discriminative binary indicator, given spam here is HTML-heavy and ham is mailing-list text.
- **Split evaluation on gateway/source or time, not uniformly at random.** Header artifacts (`X-Virus-Scanned: ClamAV … localhost`, `by amavisd-new at stat.math.ethz.ch`, `Debian amavisd-new at lunatech.com`) cluster by originating host in both splits; random CV will memorize those and overstate test accuracy.
- **Check message-ID / thread overlap between train and test** (`Message-ID`, `In-Reply-To`, `References` seen in the files) — list traffic produces near-duplicates that leak across folds.
- **Class balance:** I did not count the labels (the 15 shown in `data/spam2-train.labels` look mixed); verify before deciding on `class_weight`/thresholds. Only if the metric rewards scores should you tune a threshold — the course's measures are accuracy/error and composite measures (`resources/mlsec-perf-small.txt`, slides 5–6), and the task states the metric is identical to task 1, so confirm the exact formula on the platform before optimizing anything beyond plain accuracy.
- **Test-side format difference:** test files end in `.x` and the task explicitly warns the ending carries no label information — the reader must derive the filename→id mapping without relying on a trailing `.{0,1}`, and predictions must be emitted in whatever id the platform expects.
