- **Format & scale.** Members are complete HTML documents (not emails): `training.content_types`/`test.content_types` say 3392/2757 HTML of 3561/2757, with only 2 email-typed members per split (`email_header_rate` 0.0006/0.0007) — email-header logic is irrelevant here. Zip members are *stored* (`compress_type` 0 for all, my `names.py` output), so streaming reads are cheap; totals 76.5 MB train / 58.7 MB test (`training.inventory`, `test.inventory`).
- **A non-data member inside the train zip.** `research/names.py` shows 3562 members, one of which is `webspam-train.labels` (name length 20, shape `A-A.A`) — globbing all members gives 3562 pages, not 3561. Test has exactly 2757 (`test.inventory.samples`).
- **IDs carry no content information.** Names are 16 random lowercase letters: `training_vs_test.name_suffixes` = `{0:3007,1:554}` vs `{x:2757}`; nothing like a host/domain is recoverable from the name.
- **Imbalance is real.** `training.targets` = 3007 / 554 (15.6% spam) — balanced accuracy is the metric per `task.md`, so the minority class drives the score.
- **Spam files are byte-size-bounded: a near-free signal.** Per `training.sizes_by_target`, spam max = 23 751 B vs ham max = 1 048 589 B; my `research/words.py` confirms 0/554 spam exceed 23 751 B while 36.5% of ham do. In the test split 31.6% of members exceed 23 751 B (`words.py`) → those are almost certainly class 0 by construction, a clean ceiling for pruning. Ham's max 1 048 589 ≈ 1 MiB plus a tail (see next bullet) indicates the corpus was truncated at 1 MB; 0.4% of ham are >100 KB (`words.py`).
- **Every page carries random junk after `</html>`, which breaks hash-based dedup.** `research/comb.py`: mean 16.4 B, min 0, max 357 B of appended bytes in *both* splits (110/3561 train and 104/2757 test have no `</html>` at all). Consequence: `*.duplicates` report 0 duplicate groups and `training_vs_test.exact_overlap` = 0.0, but byte-hash equality cannot detect a reused page because of that tail — near-duplicate contamination may be hidden. It also pollutes any byte/n-gram or byte-level hashing feature; parse from the HTML body only.
- **Class-correlated structural features (medians, `research/feats.py`, 3561 members).** `<font>` tags 0 → 22 (spam has many, ham essentially none); distinct linked domains 3 → 11; absolute `http` hrefs 4 → 11; `<img>` 9 → 4; `<li>` 4 → 0; `<!doctype>` 1 → 0; `.asp` mentions 0 → 2; visible words 314 → 472. Consistent with `training.text_by_target` (lines_median 202→84, urls_median 9→25, `html_rate` 1.0 for spam vs 0.982 for ham). Spam pages are link-dense, tag-thin, font-styled; ham pages are semantic/markerup-rich.
- **Vocabulary is domain-separated, not spam-word-only.** `research/words.py` (document-frequency ratio, ≥5 docs): spam-rising = `ezze`(276), `airfare`(170), `rentals`(128), `shopshrewd`, `airfares`, `stm`, `cruises`, `airlines`, `accommodations`, `tripadvisor`, `cheap`(341), `poker`, `impress`(271); ham-rising = a UK public-sector register: `environmental`(623), `applicants`(378), `sustainability`, `conservation`, `grants`, `welfare`, `consultations`, `births`, `deaths`, `carers`, `licences`, `policing`, `offending`, `rubbish`. Top-of-corpus tokens differ: ham `nbsp, information, help, map`; spam `www, http, com, html, travel` — i.e. spam text is URL/link boilerplate. - **Ordering is safe; encodings are not.** `training.order_leakage` (764/751/750/742 zeros per archive quarter) means the zip order is not label-ordered, so a sequential split is fine. But `utf8_fraction` is 0.9992 (train) / 0.9996 (test) — decode with `errors='replace'` or `latin-1` (my scripts use `latin-1`) or the whole member is dropped; one train member is classified `binary`.
