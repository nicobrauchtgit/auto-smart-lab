- `units/clustering-of-malicious-code/malicious-code-for-web-servers/data/php-train.labels` (read in full, 657 rows): only **four** distinct family values appear — `1,2,3,4` — and the distribution is severely imbalanced: family 1 dominates (~80%), family 4 ~15%, families 2 and 3 only ~21–25 files each (~3–4%). Consequence: calibrating "the right number of clusters" or a global threshold on this train set will bias you toward 4 clusters with one giant cluster; do not hardcode k≈4 for the 355 unknown test scripts (`task.md`: "families in the two datasets are different").
- Same file: every path is `data/php-known/<16 random lowercase chars>.<family>` — the family is encoded in the filename suffix and duplicated in the label, so a naive pipeline can leak labels via filename parsing. Test names end `.x`, which "carries no information" (`task.md`), so strip the suffix and make sure no filename-derived feature (extension, length, hash of name) reaches the representation.
- Both `php-train.zip` and `php-test.zip` are present locally under `units/clustering-of-malicious-code/malicious-code-for-web-servers/data/` (found by glob), so representation and threshold can be validated on the known split before applying to the unknown split.
- Char/token n-gram vectors with **TF-IDF normalization + cosine distance**. The malware-clustering survey states that for high-dimensional sparse static features (strings, n-grams) the decisive factor is cosine/spherical geometry or TF-IDF normalization before Euclidean, which removes file-length effects — relevant here because honeypot webshells vary widely in size (`https://arxiv.org/html/2611.02380v1`).
- **Two-stage coarse → fine clustering**: cheap statistical/structural features first (file size, line count, ratio of symbols to alphanumerics, count of `?`/braces, presence of decode functions), then refinement on a finer similarity — mirrors the multistep coarse-grained/refinement pipeline that produced good family structure in HTTP-behaviour malware clustering (`https://www.usenix.org/event/nsdi10/tech/full_papers/perdisci.pdf`).
- **"Code fingerprint" set features**: enumerating static strings a shell contains (command strings, URLs/emails, magic constants, distinctive function names like `eval`, `base64_decode`, `gzinflate`, `preg_replace`, `str_rot13`, `curl_*`, `move_uploaded_file`, `chmod`) and comparing them by set/Jaccard similarity. The large web-shell study used code fingerprints for feature enumeration and found the shells are comparatively simple PHP (no OOP, minimal inter-procedural analysis), so a flat function/string-level fingerprint is tractable (`https://www.securitee.org/files/webshells_www2016.pdf`).
- Expect **obfuscation-driven drift inside a family** (same shell, re-encoded). The WWW2016 analysis documents that families evolve by obfuscation and code copying (e.g. c99 → c999, c99 code inside Fx29), and ESDA-style work puts regex/deobfuscation before feature extraction (`https://www.securitee.org/files/webshells_www2016.pdf`, `https://actsoft.org/science/act2025-pro/60-esda2025.pdf`). Worth a normalization stage that decodes base64/hex/`chr`/`gzinflate` layers and strips comments/whitespace before hashing, so variant pairs land in one group.
- **Near-duplicate-friendly hashing/sketching** (MinHash/SuperMinHash or fuzzy-hash-style n-gram sketches) on top of hierarchical clustering — shown to keep hierarchical clustering effective on large malware corpora while cutting cost, and effective because webshell collections are heavy in copy-paste variants (`https://arxiv.org/html/2611.02380v1`, `https://virusbulletin.com/virusbulletin/2019/11/dexofuzzy-android-malware-similarity-clustering-method-using-opcode-sequence`).
- n-gram **frequency histograms with a similarity ratio** as an alternative similarity for family grouping (`https://research.ijcaonline.org/volume120/number5/pxc3903960.pdf`).
- Report **homogeneity and completeness separately**, not only their harmonic mean. With ~80% of files in one family (`php-train.labels`), "put everything in one cluster" gives perfect homogeneity and zero completeness, and the reverse (every file singleton) gives the mirror failure — check both directions when calibrating on the known split.
- **Deduplicate exact/near-exact scripts before clustering**, or a dense majority family will dominate centroid/linkage choices and swallow rare families.
- Prefer **threshold-on-similarity / density-style** grouping whose cluster count emerges from the data rather than a fixed k: the training split has only 4 families but the test split is explicitly different, so k is unknown and possibly larger (`task.md`).
- Calibrate the similarity cutoff **on the train labels via the same pipeline** you will run on the test set (representation + threshold selection, not label transfer), since the task forbids supervised transfer to new families (`task.md`).
- Output hygiene: one line per unknown script `data/php-unknown/<name>.x;<group>`, deterministic sorted order over the 355 paths, and group integers starting at 0 with no gaps — only the partition matters (`task.md` output block).
